################################################################################
## Project Description
################################################################################

The Afridi Inn Restaurant Management and Online Order Tracking System is a
responsive, browser-based OLTP application for a multi-branch restaurant. It
brings dine-in and online orders into ONE order workflow and covers: menu and
price administration, order entry, butcher -> chef -> dispatch -> billing ->
completion routing, authorised cancellation, simulated payment, customer
order tracking, customer feedback and manager sales reporting.

It is built for the CS 341 course project. The primary goal is to DEMONSTRATE
database design: a normalised (3NF) PostgreSQL schema, CRUD operations,
constraints, stored procedures, triggers and views, with every SQL query
documented in the report. The web application exists to exercise that database.

The system is based on the Milestone 1 report (interview with Junaid Afridi,
manager of the Afridi Inn IBA branch). The real workflow is followed:
  - Cashier sees online orders and enters dine-in orders.
  - Meat items go to the BUTCHER first, then to the CHEF. Other items go
    straight to the chef.
  - Food goes to DISPATCH, the cashier generates the bill, the order is done.
  - Cancellation needs a MANAGER or GRO approval (recorded with a reason).
  - Only the OWNER can change menu categories, items, sizes, add-ons, prices.
  - GRO manages numbered tables; numbers that are multiples of 10 are not used.
  - Bill numbers restart at 1 every day per branch (e.g. KHI1-20261106-0001).

Features NOT confirmed by the interview are "proposed extensions" and must be
labelled as such in the UI notes and in the report: the online tracking token,
the payment record, and the feedback rating.

Users of the system:
  - Customer (no account)  : browse menu, place online order, track it with a
                             tracking token, leave feedback
  - Owner                  : menu/price maintenance, branches, staff, all data
  - Manager / General Mgr  : sales reports, approve cancellations
  - Food & Beverage Mgr    : read-only monitoring of orders and menu
  - GRO                    : tables, approve cancellations
  - Cashier                : online order queue, dine-in entry, billing, payment
  - Order Taker / Waiter   : create / modify dine-in orders
  - Butcher                : butcher queue
  - Chef                   : kitchen queue
  - Dispatch               : ready orders, hand-over

The product is a responsive web application. Every workflow must work on a
desktop browser and on a phone browser (waiters, butchers and chefs use phones
or tablets).

The visual identity: warm, clean, professional. White cards on a warm off-white
page, one confident burnt-orange primary colour, generous whitespace, readable
type, gentle rounded corners, subtle shadows. NO GRADIENTS — every colour is a
solid hex. Motion is minimal and done with Tailwind transitions only.

HARD RULES (apply to the entire project):
  1. FREE AND LOCAL ONLY. PostgreSQL + pgAdmin 4 run locally. No paid service,
     no cloud account, no credit card anywhere.
  2. PAYMENTS ARE SIMULATED. No payment gateway, no card numbers, no keys.
     The cashier (or the online customer) picks a method (Cash / Card /
     Online); the system records a dummy payment whose amount is the computed
     bill total. Every payment screen shows a visible "SIMULATED PAYMENT"
     badge.
  3. ALL SQL IS RAW AND PARAMETERISED ($1, $2 ...). No ORM. Never build SQL by
     string concatenation. This is a database course: the SQL is the product.
  4. AUTHORISATION IS ENFORCED SERVER-SIDE (route handlers + role guards) and,
     where possible, IN THE DATABASE (constraints, triggers). Hiding a button
     is never treated as security.
  5. ATOMIC LOGIC LIVES IN THE DATABASE. Order creation, status advancement,
     cancellation and payment are stored procedures/functions that run in one
     transaction. The app calls them; it does not re-implement the rules.
  6. EVERY SCHEMA CHANGE IS A NUMBERED .sql FILE in db/. Never change the live
     database by hand-editing in pgAdmin without saving the statement to a file.
  7. Passwords are stored only as bcrypt hashes. No plain-text passwords.

################################################################################
## Authentication & Access Rules
################################################################################

Staff authentication (customers have NO accounts):
  - Staff sign in with username + password (employee.username /
    employee.password_hash). Hashing: bcryptjs, cost 10.
  - On success the server issues a signed JWT (library: jose) with
    { employee_id, role, branch_id } in an httpOnly, SameSite=Lax cookie,
    8-hour expiry. No tokens in localStorage.
  - middleware.ts protects /staff/** and redirects to /staff/login.
  - Every route handler calls requireRole([...]) from src/lib/auth/guards.ts.
  - Inactive employees (is_active = false) cannot sign in.
  - Error messages are specific but safe: "Incorrect username or password".

Branch scoping:
  - Non-owner staff are tied to employee.branch_id. EVERY staff query is
    filtered by that branch_id taken from the session, never from the request.
  - Owner / head-office staff (branch_id NULL) may choose a branch from a
    branch switcher and see all branches.

Customer access:
  - No login. An online order needs customer name + phone.
  - Tracking is by tracking_token only (32 hex chars from gen_random_uuid()).
    The /track/[token] page shows that single order's public status and
    nothing else. No page lists or searches other customers' orders.

------------------------------------------------------------------------

  - Database name: afridi_inn. Database timezone: Asia/Karachi
      ALTER DATABASE afridi_inn SET timezone TO 'Asia/Karachi';

    (src/lib/db/pool.ts). Parameterised queries only.
  - Transactions: stored procedures are called with
    `SELECT sp_place_order($1, ...)` / `CALL ...`; multi-statement app logic
    uses a withTransaction(client => ...) helper in src/lib/db/tx.ts.
  - Postgres features demonstrated for the course: PRIMARY/FOREIGN/UNIQUE/
    CHECK constraints, composite keys, triggers (PL/pgSQL), stored
    functions/procedures, views, indexes, transactions, advisory locks.
  - No ORM, no query builder (no Prisma, Drizzle, Knex, Sequelize).

------------------------------------------------------------------------
Payments (SIMULATED)
------------------------------------------------------------------------

  - No Stripe, no gateway, no external call.
  - Flow: bill generated (order_status BILLED) -> cashier picks method ->
    POST /api/orders/:id/pay -> sp_record_payment() inserts/updates the
    payment row (status Paid, amount = order total from v_order_totals,
    paid_at = now) -> order COMPLETED.
  - Online orders: the customer picks "Online" at checkout; payment is a
    Pending dummy payment, marked Paid when the cashier completes the order.
  - Test data only. The UI shows a SIMULATED PAYMENT badge everywhere a
    payment is shown.

## Data Model (PostgreSQL)  — from Milestone 1
################################################################################

13 tables (see db/01_tables.sql for the exact DDL):

  branch              branch_id PK · branch_code UQ · branch_name · phone ·
                      address · is_active
  employee            employee_id PK · branch_id FK(null) · full_name · nic UQ ·
                      role · staff_level · username UQ* · password_hash* ·
                      is_active
  menu_category       category_id PK · category_name UQ · description · is_active
  menu_item           menu_item_id PK · category_id FK · item_name ·
                      description · requires_butcher · is_available
  menu_item_size      size_id PK · menu_item_id FK · size_label · price
  add_on              add_on_id PK · add_on_name UQ · price · is_available
  restaurant_table    table_id PK · branch_id FK · table_no · capacity · status
  customer            customer_id PK · customer_name · phone UQ · created_at
  customer_order      order_id PK · branch_id FK · customer_id FK(null) ·
                      table_id FK(null) · created_by / assigned_butcher /
                      assigned_chef / dispatched_by / cashier / approved_by
                      (six employee FKs, all null) · order_channel ·
                      order_date · daily_order_number · bill_number UQ ·
                      tracking_token UQ(null) · order_status ·
                      special_instructions · cancellation_reason ·
                      created_at · updated_at
  order_item          order_item_id PK · order_id FK · size_id FK · quantity ·
                      unit_price_at_order · line_status · item_notes
  order_item_add_on   (order_item_id, add_on_id) composite PK · quantity ·
                      unit_price_at_order
  customer_feedback   feedback_id PK · customer_id FK · order_id FK(null) ·
                      rating 1-5 · comments · submitted_at
  payment             payment_id PK · order_id FK UQ · method_name ·
                      payment_status · amount* · paid_at*

  * = small additions to the Milestone 1 schema (login credentials for staff,
      dummy payment amount/time). Mention them in the report's schema section.
  Also added: UNIQUE(branch_id, table_no) and UNIQUE(menu_item_id, size_label).

------------------------------------------------------------------------
Allowed Values (CHECK constraints)
------------------------------------------------------------------------

  employee.role    : OWNER, MANAGER, FB_MANAGER, GRO, ORDER_TAKER, WAITER,
                     CASHIER, CHEF, BUTCHER, DISPATCH
  staff_level      : Senior, Junior
  order_channel    : DINE_IN, ONLINE
  order_status     : PLACED, AT_BUTCHER, AT_CHEF, READY, DISPATCHED, BILLED,

  line_status      : PENDING, AT_BUTCHER, BUTCHER_DONE, COOKING, READY,

  payment method   : Cash, Card, Online
  payment status   : Pending, Paid, Failed

------------------------------------------------------------------------
Order Workflow (status transitions)
------------------------------------------------------------------------

  DINE-IN   created by staff -> goes straight to the kitchen:
            AT_BUTCHER (if any line requires_butcher) or AT_CHEF
  ONLINE    created by customer -> PLACED (cashier must confirm) ->
            AT_BUTCHER or AT_CHEF
  Then      AT_BUTCHER -> (butcher marks lines BUTCHER_DONE) -> AT_CHEF ->
            (chef marks lines READY) -> READY -> DISPATCHED (dispatch hands
            over) -> BILLED (cashier generates bill) -> COMPLETED (payment
            recorded)
  Cancel    any status before COMPLETED -> CANCELLED (approver + reason)

  Line flow  : requires_butcher lines  PENDING -> AT_BUTCHER -> BUTCHER_DONE
                                       -> COOKING -> READY
               other lines             PENDING -> COOKING -> READY
  The order status rolls up from its lines inside sp_advance_line().

------------------------------------------------------------------------
Stored Procedures / Functions (db/02 and db/03)
------------------------------------------------------------------------

  sp_place_order(branch_id, channel, table_id, customer_name, customer_phone,
                 employee_id, instructions, items jsonb) RETURNS order_id
    - upserts the customer by phone (online orders)
    - inserts customer_order (numbers/token filled by trigger)
    - for each item: looks up the CURRENT price from menu_item_size / add_on
      and stores it as unit_price_at_order (price snapshot); sets line_status
      by requires_butcher; inserts order_item_add_on rows
    - sets initial order_status (PLACED for online, else AT_BUTCHER/AT_CHEF)
    - sets the table to Occupied for dine-in
    - items jsonb: [{size_id, quantity, notes, add_ons:[{add_on_id,quantity}]}]
  sp_confirm_online_order(order_id, cashier_id)
  sp_advance_line(order_item_id, new_status, employee_id)
    - validates the transition, records butcher/chef employee, rolls up the
      order status
  sp_dispatch_order(order_id, employee_id)
  sp_generate_bill(order_id, cashier_id)      -> status BILLED, table 'Billing'
  sp_record_payment(order_id, method, cashier_id)  -> simulated; status
                                                  COMPLETED, table 'Available'
  sp_cancel_order(order_id, approver_id, reason)   -> CANCELLED, lines
                                                  CANCELLED, table freed

------------------------------------------------------------------------
Triggers (db/02)
------------------------------------------------------------------------

  trg_assign_order_number   BEFORE INSERT on customer_order
      - takes pg_advisory_xact_lock(branch_id, yyyymmdd) so concurrent orders
        cannot get the same number
      - daily_order_number = MAX(...)+1 for (branch, order_date)
      - bill_number = BRANCHCODE-YYYYMMDD-NNNN
      - tracking_token = replace(gen_random_uuid()::text,'-','') for ONLINE
  trg_check_cancel_approver BEFORE INSERT/UPDATE on customer_order
      - if approved_by_employee_id is set, that employee must be an active
        MANAGER or GRO
  trg_set_updated_at        BEFORE UPDATE on customer_order
  trg_block_edit_after_bill BEFORE INSERT/UPDATE/DELETE on order_item
      - items cannot change once the order is BILLED/COMPLETED/CANCELLED
  trg_owner_only_menu       OPTIONAL (app-level role check is mandatory;
      a DB trigger using a session variable `app.employee_role` is a bonus)

------------------------------------------------------------------------
Views (db/03)
------------------------------------------------------------------------

  v_order_totals   order_id, items_total, add_ons_total, grand_total
  v_menu_full      category, item, size, price, requires_butcher, available
  v_butcher_queue  order lines at AT_BUTCHER with order/table info
  v_kitchen_queue  order lines needing the chef
  v_sales_report   date, branch, item, size, qty sold, revenue (COMPLETED only)
  v_order_tracking public-safe columns only (bill_number, status, channel,
                   created_at, tracking_token) — no phone, no employee data

------------------------------------------------------------------------
Default Business Rules (decisions taken so the build is unblocked; each lives
in src/lib/constants.ts and/or the SQL and can be changed without redesign)
------------------------------------------------------------------------

  - Business date    : Asia/Karachi calendar date.
  - Bill total       : sum(quantity * unit_price_at_order) + add-ons
                       (quantity * unit_price_at_order). No tax/service charge
                       (not confirmed by the interview).
  - Modify order     : allowed until BILLED. Lines may be added/removed/changed
                       (quantity, notes) while the order is not billed.
  - Cancellation     : allowed before COMPLETED; needs approver + reason
                       (min 5 characters). No refund logic (payments are dummy).
  - Menu deletion    : items/categories with order history are DEACTIVATED
                       (is_available / is_active = false), never deleted.
  - Price changes    : affect only future orders (snapshots protect history).
  - Online order     : customer supplies name + phone; the same phone re-uses
                       the existing customer row.
  - Tracking page    : shows a 6-step progress bar mapped from order_status.
  - Feedback         : one per customer per order; allowed once the order is
                       COMPLETED; reached from the tracking page.
  - Seed accounts    : every demo user shares the password "Afridi@2026"
                       (bcrypt-hashed in seed). Change before any real use.

################################################################################
## API Routes (Server-Side Business Logic)
################################################################################

  Every route: validate input with zod -> read session (except public routes)
  -> requireRole([...]) -> scope by session branch_id -> call a function in
  src/lib/queries or a stored procedure -> return typed JSON.

  Public routes (no session): GET /api/menu · POST /api/orders/online ·
  GET /api/tracking/[token] · POST /api/feedback.

  Error format: { error: { code, message } } with correct HTTP status
  (400 validation, 401 unauthenticated, 403 forbidden, 404, 409 conflict —
  e.g. table already occupied / invalid status transition, 500). Database
  constraint errors (SQLSTATE 23xxx, P0001 from RAISE EXCEPTION) are mapped to
  friendly messages in one helper, src/lib/db/errors.ts.

################################################################################
## Security & Integrity Notes
################################################################################

  - Parameterised queries only (SQL-injection safe). Lint rule / code review:
    no template-literal SQL with interpolated user input.
  - Tracking tokens are 128-bit random (gen_random_uuid), unique, and the
    tracking view exposes no personal data beyond the order itself.
  - Role checks in every route handler; branch filter from the session only.
  - The database enforces the rules even if the app is bypassed: CHECKs,
    UNIQUEs, FKs, the approver trigger, the item-lock trigger, the numbering
    trigger.
  - Daily order numbers are allocated under an advisory lock, so two cashiers
    placing orders at the same instant cannot receive the same number
    (test with two pgAdmin Query Tool windows).
  - Price snapshots (unit_price_at_order) protect history from price edits.
  - Staff passwords: bcrypt. Session cookie: httpOnly, SameSite=Lax.
  - Rate-limit the login route (simple in-memory counter: 5 failures / 10 min
    per username + IP) and the public online-order route.

################################################################################
## Performance Notes
################################################################################

  - Server components for read-only pages; client components for carts,
    polling queues and forms.
  - Indexes (already in 01_tables.sql): customer_order(branch_id, order_date),
    customer_order(order_status), order_item(order_id), order_item(size_id),
    menu_item(category_id) and all UNIQUE constraints. Use EXPLAIN ANALYZE in
    pgAdmin on the sales report query and include one screenshot.
  - Single pg Pool (max 10). Never create a Pool per request.
  - recharts is dynamically imported.
  - Queue polling every 5 s only while the tab is visible.
